# LogPulse RTBDA Presentation Guide

This document is an extensive, presentation-ready description of the LogPulse project for Real-Time Big Data Analytics (RTBDA). It includes architecture context, diagrams, and clear explanations of the speed, batch, and serving layers.

---

## 1) What is LogPulse?

LogPulse is a full-stack observability sandbox that simulates real-time log ingestion, anomaly detection, batch analytics, and root-cause analysis (RCA). It is designed to demonstrate RTBDA concepts using a modern data pipeline and an interactive dashboard.

The project shows how high-volume events are:

- Generated or ingested in real time
- Enriched and scored for anomalies
- Persisted for history and reporting
- Analyzed in batch for aggregated insights
- Served to a frontend using APIs and WebSockets

---

## 2) Why RTBDA? (Project Objective)

Real-Time Big Data Analytics focuses on turning continuous streams of data into actionable insights with minimal delay, while still supporting historical summaries and deeper analysis. LogPulse demonstrates the classic RTBDA pattern:

- Speed layer for live metrics and alerts
- Batch layer for aggregated summaries
- Serving layer to expose results

This mirrors the architecture used in production observability, fraud detection, monitoring, and large-scale telemetry systems.

---

## 3) High-Level Architecture (Lambda-Style)

LogPulse follows a Lambda-style RTBDA architecture with speed, batch, and serving layers.

```text
Operator/Analyst
    |
    v
Frontend (Bun + React + Vite)
  - Pages (Live Logs, Anomalies, Metrics, Batch, Agent)
  - React Query Hooks
  - WebSockets (/ws/logs, /ws/anomalies, /ws/metrics)
    |
    v
Backend API (FastAPI)
  - REST (/api/v1/*)
  - WebSockets (/ws/*)
  - Stream Pipeline (buffers, metrics)
    |
    +--> Log Generator --> Detection Enrichment --> Kafka Publisher --> Kafka (logs.raw)
    |                       |                         |
    |                       v                         v
    |                   PostgreSQL <--- Kafka Consumer Worker
    |                       ^
    |                       |
    +--> Batch Scheduler --> Aggregate Job (PySpark/Python) --> PostgreSQL
    |
    +--> RCA Queue --> Agent Worker --> Orchestrator --> LLM (Gemini/OpenAI)
                            |                          |
                            v                          v
                         PostgreSQL <------------------+

Infra: Zookeeper <-> Kafka, Redis (provisioned), Elasticsearch (provisioned)
```

## 4) RTBDA Layers in LogPulse

### A) Speed Layer (Real-Time Stream)

**Goal:** Process data with minimal delay and show live results.

**How it works:**

- Synthetic logs are generated by the backend and enriched with anomaly scores.
- Events are written to Postgres and published to Kafka `logs.raw`.
- The stream consumer reads Kafka and updates real-time buffers.
- WebSockets stream logs, anomalies, and metrics to the UI.

**Why it matters:**

This layer provides immediate feedback and live monitoring, which is critical for alerting and operational response.

---

### B) Batch Layer (Historical Aggregation)

**Goal:** Produce stable, reportable summaries over larger windows.

**How it works:**

- A batch scheduler collects recent events.
- Aggregation runs in PySpark if available, otherwise a Python fallback is used.
- Summaries are persisted to `batch_runs` in Postgres.
- UI shows batch status and historical summaries.

**Why it matters:**

Batch analytics help validate trends and give a longer-term view that complements the real-time stream.

---

### C) Serving Layer (API + WebSocket Interface)

**Goal:** Provide one interface for both real-time and batch insights.

**How it works:**

- REST endpoints expose logs, anomalies, batch stats, and RCA reports.
- WebSocket endpoints stream live events and metrics.
- Frontend consumes both for a complete observability view.

**Why it matters:**

This layer unifies the speed and batch results and makes them accessible for dashboards and queries.

## 5) Detailed Stream Flow (Speed Layer)

```text
User -> UI -> API (/logs/generate)
API -> Log Generator -> Detection Enrichment
Detection Enrichment -> Postgres (raw_log_events)
Detection Enrichment -> Kafka Publisher -> Kafka (logs.raw)
API -> WebSocket register_event

Stream Worker:
    Kafka (logs.raw) -> Stream Worker -> Detection Enrichment -> Postgres
    Stream Worker -> WebSocket register_event

UI Subscriptions:
    UI -> /ws/logs, /ws/anomalies, /ws/metrics -> Live updates
```

---

## 6) Batch Analytics Flow

```text
User -> API (/batch/run)
API -> Batch Scheduler -> Aggregate Job -> In-memory Snapshot

If PySpark enabled:
    Aggregate Job -> PySpark -> Aggregated summary
Else:
    Aggregate Job -> Python Aggregator -> Aggregated summary

Batch Scheduler -> Postgres (batch_runs) -> API response
```

---

## 7) RCA Agent Flow

```text
User -> UI -> API (/agent/analyze)
API -> Postgres (rca_reports: status=queued)
API -> UI (report_id)

Agent Worker loop:
    Postgres (queued) -> Worker -> Orchestrator -> Tools -> Postgres
    Orchestrator -> LLM (Gemini/OpenAI) -> RCA JSON
    Orchestrator -> Postgres (status=completed/failed)

UI -> API (/agent/reports) -> RCA report payload
```

## 9) Tools and Technologies Used

**Backend**

- Python 3.12
- FastAPI (REST + WebSocket API)
- uv (dependency and runtime)
- SQLAlchemy (persistence)

**Streaming**

- Kafka topic `logs.raw`
- Kafka consumer worker for stream processing

**Batch**

- PySpark when available
- Python fallback aggregator

**Storage**

- Postgres for events, batch runs, RCA reports
- Redis and Elasticsearch are provisioned for future use

**Frontend**

- Bun + Vite + React
- shadcn UI components
- React Query for API calls and caching

**RCA Agent**

- Gemini as primary LLM
- OpenAI as fallback
- Tool-driven RCA prompt orchestration

## 10) How to Explain It in a Presentation

Suggested narrative:

1. **Problem**: We need to analyze large log streams in real time, but also keep batch summaries for reporting.
2. **Architecture**: We implement a Lambda-style RTBDA system with speed, batch, and serving layers.
3. **Speed Layer**: Stream pipeline for live logs and anomalies; WebSockets push results to UI.
4. **Batch Layer**: Scheduled aggregation for historical summaries using PySpark or Python.
5. **Serving Layer**: REST + WebSockets expose data to the frontend.
6. **RCA Agent**: Asynchronous analysis that explains anomalies with LLM-based reasoning.
7. **Outcome**: A full-stack RTBDA demo with real-time visibility and batch analytics.
